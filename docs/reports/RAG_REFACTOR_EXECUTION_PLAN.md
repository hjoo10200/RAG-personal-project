# 청년 독립 RAG 개편 실행계획

작성일: 2026-08-31

> 후속 구현: [최신 개편 설명서](RAG_REFACTOR_IMPLEMENTATION.md)를 참고하세요. 숫자는 셀렉트 구간 대신 직접 입력하며, [공식 비용 기준](COST_REFERENCE_RESEARCH_20260831.md)을 수집·적용했습니다. 아래 내용은 최초 실행계획의 기록이고 완료 확인표가 아닙니다. 최신 변경의 실행 검증은 사용자가 수행합니다.

상태: 실행계획입니다. 이 문서 작성 과정에서는 애플리케이션 코드 수정, 라이브러리 설치, DB 적재, 검색·생성·평가 실행을 하지 않았습니다. 아래 파일명과 단계는 구현 제안이며, 새 모듈이 이미 존재한다는 뜻이 아닙니다.

## 1. 이번 개편의 확정 방향

1. 사용자는 셀렉트 폼에서 상황을 선택합니다. 자유문장 작성과 세부 생활비 입력을 요구하지 않습니다.
2. 보고서 경로에서는 검색 전에 자금 계산과 재정 상황 판단을 수행합니다.
3. 재정 판단 결과와 목적·지역·시기·우선순위로 내부 검색 질의를 만듭니다.
4. 보고서 RAG는 guides·cases를 검색해 독립 실행 방법을 설명합니다.
5. 정책 검색은 policies를 사용하는 독립 기능으로 분리합니다. 보고서 생성 성공 여부에 의존하지 않습니다.
6. 지원공고의 룰 기반 자격 분류는 구현하지 않습니다. 재정 계산 결과의 상황 판단과 혼동하지 않습니다.
7. 기존 pgvector·Elasticsearch·RRF·LangChain을 재사용합니다. 별도 서버나 새 DB 제품은 도입하지 않습니다.
8. 대시보드용 대규모 통합 payload 설계는 이번 우선 범위에서 제외합니다. 실행·검증에 필요한 작은 내부 데이터 계약만 정의합니다.

과거 조사 문서의 정책 자격 룰엔진 제안은 이번 실행계획에서 채택하지 않습니다. 계산 정의는 [자금 계획 계산식](INDEPENDENCE_COST_FORMULAS.md), 개편 전 구현은 [현재 플로우차트](CURRENT_RAG_FLOWCHART.md)를 참고합니다.

## 2. 목표 실행 경로

### 독립 보고서 경로

1. 셀렉트 선택값 JSON을 검증·정규화합니다.
2. 지역·주거 선호 등으로 사전에 검증한 비용 기준자료를 선택합니다.
3. 가용 자금·수입 구간과 비용 가정으로 계산합니다.
4. 계산 가능 여부, 초기 자금 부족 여부, 월 적자 여부 등을 판단합니다.
5. 판단 결과와 나머지 상황으로 guides·cases 검색 질의를 구성합니다.
6. 벡터 검색과 BM25 검색을 RRF로 결합해 근거를 확보합니다.
7. 원래 입력·계산 결과·판단·근거로 개인별 보고서를 작성하고 검증합니다.

지역과 주거 형태는 비용 기준 선택과 문서 검색에 모두 사용할 수 있습니다. ‘계산에 쓴 입력은 이후 사용하지 않는다’는 배타적 분리는 하지 않습니다. 숫자를 질의에 모두 붙이는 대신 계산에서 확인된 제약을 검색 목적에 반영합니다.

### 정책 검색 경로

1. 동일한 선택값 중 연령·현재 지역·희망 지역·고용·학업·주거 정보를 활용합니다.
2. policies 전용 검색 질의를 구성합니다.
3. 하이브리드 검색 후 정책·공고 단위로 중복 결과를 묶습니다.
4. 지원 내용, 주요 조건, 접수 정보, 신청 경로와 원문을 표시합니다.
5. 필요할 때만 별도의 LLM 요약을 제공합니다. 후보 검색 자체에는 보고서 생성이 필요하지 않습니다.

재정 판단 결과가 있으면 검색 주제를 보완할 수 있지만 필수 인자로 만들지 않습니다. 정책 결과를 보고서 생성기에 반드시 넘기거나 미선정 지원금을 기본 자금에 더하지 않습니다.

## 3. 현재 코드에서 반드시 해소할 결합

| 현재 위치 | 확인한 상태 | 개편 작업 |
| --- | --- | --- |
| `src/generation/report_schema.py` | 정수 금액·자유문자열 입력과 생성 스키마가 함께 존재 | 공통 선택형 입력 계약 분리, 구간·미정 처리 |
| `src/run_rag.py` | 검색 후 생성기 호출 | 계산·판단을 검색 앞으로 이동 |
| `src/retrieval/hybrid_pipeline.py` | 모든 `CORPUS_NAMES`의 DB와 인덱스를 확인·검색 | 요청한 코퍼스만 확인·검색하도록 공통 함수화 |
| `src/retrieval/rag_pipeline.py` | 상황 문자열 기반 질의, 일부 주제·연도 고정 | 보고서용 질의와 정책용 질의 분리 |
| `src/retrieval/keyword_query_builder.py` | 보고서·정책 질의가 한 함수에 묶임 | 기능별 질의 구성, 선택 코드에 따른 명확한 분기 |
| `src/generation/report_generator.py` | 생성 직전에 `_build_financial_context()` 실행 | 계산을 별도 모듈로 옮기고 생성기는 결과를 전달받음 |
| 같은 파일의 프롬프트·검증 | 정책 문단과 정책 근거를 요구 | 보고서에서 정책 의존 제거 |
| `NarrativeDraft`·`NarrativeReport` | 정책 필드·4개 소제목·정책 필수 주제 검사 | 보고서 전용 구조와 검증을 함께 변경 |
| `src/ragas/`·기존 테스트 | 기존 입력·정책 포함 보고서·검색 경로에 의존 | 새 입력과 분리된 실행 경로에 맞춰 수정 |

정책 질의에는 `2026`과 일부 서울 정책명이 고정되어 있습니다. 이 부분을 제거하되 현재 연도를 붙이는 것만으로 정책 최신화가 구현됐다고 보지 않습니다. 현재의 문자열 분기에서 ‘미취업’이 ‘취업’에도 일치할 수 있는 문제는 선택 코드 기반 질의 구성으로 함께 해결합니다.

## 4. 단계별 실행계획

### 0단계. 기존 결과와 실행 조건 보존

작업:

- 기존 입력·검색 근거·보고서·RAGAS 결과 중 비교할 파일을 선정하고 경로를 기록합니다.
- 코드 버전, 모델·임베딩 설정, 코퍼스별 데이터 상태를 기록합니다. API 키는 기록하지 않습니다.
- 기존 오프라인 테스트 결과를 확보합니다. 새 출력은 별도 실행 디렉토리를 사용해 이전 파일을 덮어쓰지 않습니다.
- 기존 PDF·chunk_id·임베딩·인덱스를 유지합니다. 구조 개편만을 이유로 재적재하지 않습니다.

완료 기준: 개편 전 결과를 다시 찾을 수 있고, 이후 출력과 섞이지 않습니다. 이 단계에서 확보하지 못한 평가지표는 없는 상태로 기록합니다.

### 1단계. 선택형 입력 계약과 시험 입력 확정

작업:

- 선택 항목의 내부 코드와 표시명을 분리합니다. 자유문장을 파싱해서 상황을 추측하지 않습니다.
- 기본 항목: 가용 자금 구간, 수입 상태·구간, 목적, 지역, 시기, 주거 선호, 우선순위.
- 정책용 항목: 연령, 현재 지역, 고용·학업 상태 등 필요한 선택값.
- 필수 기존 지출은 없음·있음·모름으로 구분하고, 있으면 합계 구간을 선택하도록 설계합니다.
- 금액 구간의 경계 포함 여부, 상한 없음, 미정, 수입 없음과 미확인을 명시합니다.
- 현금은 현재 사용 가능한 금액, 수입은 독립 후 정기 실수령액이라는 의미를 명확히 합니다. 예정 수입은 확정 수입과 구별합니다.
- 기존 정확한 숫자의 입력은 별도 구버전 검산 사례로 보존합니다. 구간의 중간값을 기존 정수 필드에 조용히 넣지 않습니다.

예상 변경: `src/common/input_schema.py` 신설, `report_schema.py`의 공통 입력 import 정리, `examples/inputs/`에 새 버전 예시 추가.

완료 기준: 자연어와 상세 비용이 없는 JSON을 읽을 수 있습니다. 유효하지 않은 코드, 겹치는 구간, 모름을 0으로 바꾸는 변환을 테스트로 차단합니다. UI는 나중에 같은 계약을 사용합니다.

### 2단계. 검색 전 계산에 사용할 최소 비용 기준자료 준비

이 단계가 계산 구현의 선행 조건입니다. 자금과 수입만으로 초기 부족액·월 적자를 계산할 수는 없습니다.

작업:

- 우선 지원할 한 지역과 제한된 주거 유형을 정합니다. 현재 예시의 서울·월세를 첫 후보로 삼되 지역 내 비용 차이를 확인한 뒤 적용 범위를 확정합니다.
- 관련 임대 조건, 주거비 외 생활비, 이사·초기 준비비의 근거를 확인해 작은 기준표를 만듭니다.
- 출처, 관측 시점, 적용 지역·대상, 포함 항목, 추정 범위, 검토일을 함께 기록합니다.
- 자료 관측값과 프로젝트의 예비금·적립금 가정을 구분합니다. 임의의 비율을 공식 기준처럼 적용하지 않습니다.
- 보증금·월세 조합을 유지하고 관리비·생활비 중복을 제거합니다. 과거 계약을 현재 입주 가능한 매물로 표현하지 않습니다.
- 기준이 없는 지역·유형은 ‘해당 계산 미지원/근거 부족’으로 처리합니다. 보고서의 실행 안내는 계속 제공할 수 있게 합니다.

예상 추가: 검토된 `knowledge_base/metadata/cost_references.json`과 이를 읽는 작은 모듈. 처음부터 실시간 API·전국 가격 예측·새 DB를 만들지 않습니다. 파일명은 구현 시 확정합니다.

완료 기준: 적어도 한 지원 범위의 계산 가정에 추적 가능한 근거가 있습니다. 근거 없는 값은 테스트용 가상값으로만 격리합니다. 자료가 부족하면 부족한 계산을 명시하고, 완전한 비용 판단 기능으로 완료 처리하지 않습니다.

### 3단계. 계산 모듈과 재정 상황 판단 구현

작업:

- [계산식 문서](INDEPENDENCE_COST_FORMULAS.md)의 초기 필요 자금·잔액·월 지출·월 잔액·주거비 역산을 순수 함수로 구현합니다.
- API나 DB를 호출하지 않는 계산 모듈로 작성합니다. 입력 선택값과 2단계 비용 기준이 계산 재료입니다.
- 계산 결과에는 단위, 범위, 사용한 비용 기준, 가정, 누락 항목을 남깁니다.
- 재정 판단은 하나의 독립 점수가 아닌 별도의 상태들로 표현합니다.

| 판단 축 | 결과 예시 |
| --- | --- |
| 계산 범위 | 계산 완료 / 부분 계산 / 계산 불가 |
| 초기 자금 | 해당 가정에서 부족 / 비음수 잔액 / 구간에 따라 달라짐 / 정보 부족 |
| 월 현금흐름 | 해당 가정에서 적자 / 비음수 잔액 / 구간에 따라 달라짐 / 정보 부족 |

구간 전체가 음수일 때와 0을 걸칠 때를 구분합니다. 비용이 빠진 상태의 양수 잔액을 ‘충분’으로 판정하지 않습니다. 각 상태는 어떤 계산 결과에서 나왔는지 연결합니다. 초기 자금이 남아도 월 적자일 수 있으므로 서로 덮어쓰지 않습니다.

예상 추가: `src/finance/` 안에 계산 결과 스키마, 비용 기준 로딩, 계산, 재정 판단의 최소 모듈. 실제 분할은 작은 함수 규모에 맞춥니다.

완료 기준: 외부 호출 없이 산술·구간 경계·상한 없음·0과 미정·중복 항목·적자·일부 비용 누락을 검증합니다. 동일한 입력·기준 버전으로 동일한 결과가 나옵니다.

### 4단계. 검색 대상 분리와 보고서 경로 개편

작업:

- 공통 하이브리드 검색 함수에 대상 코퍼스를 명시합니다. 보고서는 guides·cases만, 정책 검색은 policies만 사용합니다.
- 선택하지 않은 코퍼스의 DB 개수 검사·질의 생성·연결 준비를 실행하지 않습니다.
- 보고서 질의 생성기가 입력과 재정 판단을 받도록 변경합니다. 초기 부족·월 적자·정보 부족의 검색 목적을 구분합니다.
- 수치가 부족할 때도 기본 집 탐색·계약·이사 관련 검색을 유지합니다. ‘정보 부족’을 검색 중단 조건으로 만들지 않습니다.
- 의미 질의와 키워드 질의는 우선 템플릿으로 구성합니다. 질의 생성을 위해 LLM을 추가 호출하지 않습니다.
- `_build_financial_context()`의 책임을 3단계로 이동하고, 동일 계산을 생성 직전에 다시 수행하지 않습니다.
- 프롬프트, `NarrativeDraft`, `SECTION_LAYOUT`, 정책 근거 검사, `NarrativeReport`의 정책 주제 요구, 관련 테스트를 함께 수정합니다.
- 보고서 구성은 ‘독립 방향과 자금 활용’, ‘집 탐색·계약·이사 실행 순서’, ‘주의점’의 세 부분을 우선안으로 합니다. 상세 분량은 시험 결과로 조정하며 과도한 최소 길이 제한을 추가하지 않습니다.
- 목표지역·주거 선호 등이 미정일 때 기존 개인화 문자열 검사가 불필요하게 실패하지 않도록 수정합니다.

예상 변경: `src/run_rag.py`, `src/retrieval/hybrid_pipeline.py`, 질의 구성 함수, `src/generation/`의 생성·검증 코드, `tests/test_report_generation.py`.

완료 기준:

- 정책 인덱스·컬렉션이 비어 있는 조건을 모의해도 보고서 경로가 해당 저장소를 조회하지 않고 진행합니다.
- 검색 전에 계산·판단이 완료되며, 질의에서 그 판단과 사용자 우선순위를 확인할 수 있습니다.
- 정책 문단·정책 근거 없이 보고서가 검증을 통과합니다.
- 보고서가 입력·계산 가정을 실제 사실로 바꾸지 않습니다.

공유하는 pgvector나 Elasticsearch 서비스 전체의 장애까지 서로 격리한다는 의미는 아닙니다. 이번 목표는 불필요한 정책 데이터 의존과 실행 순서 의존을 제거하는 것입니다.

### 5단계. 독립 정책 검색 엔진 구현

작업:

- `src/run_policy_search.py` 등의 별도 진입점과 정책 검색용 함수를 만듭니다.
- 정책 엔진은 공통 입력만으로 실행됩니다. 재정 판단 결과는 선택적인 검색 보조 정보입니다.
- 연령·지역·고용·학업·주거 상태에 맞는 질의를 만들고, 고정된 서울 정책명과 단일 연도 의존을 줄입니다.
- 같은 정책의 다른 모집 회차·정정 버전을 무조건 하나로 합치지 않습니다. 먼저 공고 문서 기준으로 묶고 확인된 식별 정보가 있을 때 정책별로 정리합니다.
- 검색 결과에는 정책명, 지원 내용, 주요 조건, 접수 정보, 신청 경로, 원문 출처와 확인 가능한 기준 시점을 담습니다.
- 정보가 없는 항목은 미확인으로 둡니다. 모집 기간·신청 URL을 모델이 생성하지 않도록 합니다.
- 기존 metadata에 제목·출처·기간이 부족한지 점검하고, 필요한 문서만 보완합니다. 만료된 공고를 현재 모집 중이라고 표시하지 않습니다.
- LLM 요약은 후보 검색 이후의 선택 단계로 둡니다. 요약 실패 시에도 원문 검색 결과는 반환합니다.
- ‘관련 후보·확인할 조건’을 설명하며, 지원 자격 합격/불합격이나 수혜 확률을 출력하지 않습니다.

예상 변경·추가: 정책 전용 질의와 실행 함수, 공통 검색의 policies 호출, 별도 정책 결과 스키마·테스트. 기존 검색 메타데이터 구조를 우선 재사용합니다.

완료 기준: 계산기·보고서 생성기를 호출하지 않고 정책 검색이 실행됩니다. guides·cases 저장소 상태를 검사하지 않습니다. 결과 없음·기간 미확인·요약 실패를 구별합니다. 실제 출처 없는 신청 경로를 출력하지 않습니다.

### 6단계. 선택형 화면 연결

백엔드 JSON 경로를 확인한 뒤 최소 화면을 연결합니다. 프레임워크 선택은 이 계획에서 새로 확정하지 않습니다.

작업:

- 1단계 선택지 정의를 폼에서 그대로 사용합니다. 자유문장 입력은 필수로 두지 않습니다.
- ‘독립 보고서 생성’과 ‘지원정책 검색’을 각각 실행할 수 있게 합니다.
- 정책만 다시 검색할 때 계산·보고서 생성을 재실행하지 않습니다.
- 한 기능의 결과 없음·실패를 다른 기능의 실패로 표시하지 않습니다.
- 보고서는 문단으로, 정책은 목록으로 표시합니다. 복잡한 대시보드·차트는 이번 단계에 넣지 않습니다.

완료 기준: 셀렉트 선택만으로 두 기능을 각각 사용할 수 있습니다. 화면의 선택과 백엔드 입력 의미가 일치하고, 금액 구간을 실제 단일 금액으로 변환하지 않습니다.

### 7단계. 단계별 평가 및 최종 회귀 검증

이 단계의 테스트를 마지막까지 미루지는 않습니다. 각 단계의 오프라인 테스트를 먼저 통과시키고 통합 후 실제 검색·생성을 소규모로 평가합니다.

| 검증 대상 | 확인 방법 |
| --- | --- |
| 선택형 입력 | 코드·구간·미정 처리 단위 테스트 |
| 계산 | 정답이 있는 산술·경계값·중복·누락 테스트 |
| 재정 판단 | 같은 계산에서 일관된 상태와 이유가 나오는지 검증 |
| 질의 구성 | 조건별 스냅샷과 사례·가이드 검색 목적 확인 |
| 기능 분리 | 비대상 코퍼스 미조회, 정책 요약 실패와 보고서 독립성 검증 |
| 보고서 RAG | 관련 근거 검색, 문서 기반 주장, 개인별 실행 구체성 평가 |
| 정책 검색 | 관련 공고 검색·중복·회차·원문·기간 정보 평가 |

`src/ragas/test_dataset.py`, `response_dataset.py`, `ragas.py`를 새 입력 계약과 보고서 경로에 맞게 수정합니다. 기존 정책 포함 보고서 결과와 새 결과는 과제가 다르므로 점수를 그대로 일대일 비교하지 않습니다. 공통으로 비교 가능한 안내·사례 질문을 따로 유지합니다.

보고서 평가에서는 문서 근거 주장과 계산·사용자 입력 근거 주장을 구별합니다. 검색 근거뿐 아니라 계산에 사용한 가정과 산출값도 평가자가 볼 수 있도록 별도 기록하되, 이를 검색으로 찾은 문서처럼 위장하지 않습니다. 평가용 컨텍스트 구성을 바꾸면 버전을 남기고 이전 faithfulness와 단순 비교하지 않습니다. 계산의 정확성은 RAGAS 대신 단위 테스트로 검증합니다.

recall을 평가할 때는 기준 답변·근거가 있는 평가 행을 준비합니다. 측정 불가능한 행·실패한 지표를 제외한 평균만 성공처럼 보여주지 않고, 측정 수·미측정 수·실패 이유를 함께 기록합니다.

완료 기준: 오프라인 회귀 테스트와 소규모 실제 경로 시험을 통과하고, 평가 데이터·결과·실행 설정이 재현 가능한 형태로 보존됩니다. 점수 향상을 미리 보장하지 않습니다.

## 5. 최소 시험 시나리오

1. 정기 수입이 있고 비용 기준자료가 맞는 첫 자취 상황.
2. 초기 자금 부족이지만 월 지출은 감당하는 상황.
3. 초기 자금은 확보되지만 월 적자가 예상되는 상황.
4. 선택 구간에 따라 잔액 부호가 달라지는 상황.
5. 수입 없음과 수입 모름을 각각 선택한 상황.
6. 주거 형태 또는 세부 지역 미정인 상황.
7. 비용 기준자료가 없는 지역에서 실행 방법만 안내하는 상황.
8. 정책 저장소에 데이터가 없어도 보고서를 만드는 상황.
9. 보고서용 저장소를 조회하지 않고 정책만 검색하는 상황.
10. 과거 공고·접수 정보 미확인·검색 결과 없음·요약 실패 상황.

테스트용 가상 비용과 실제 사용자용 비용 자료를 분리합니다. 실사용 가능 여부를 확인하는 시험에서는 테스트 PDF나 가상 근거를 실제 근거처럼 사용하지 않습니다.

## 6. 출력 보존과 호환성

- 보고서 최종 출력은 기존의 제목·Markdown 본문 JSON 형태를 우선 유지합니다. 내부 세 문단 구조와 기존 네 문단 구조의 차이는 버전으로 구분합니다.
- 정책 결과는 별도 파일로 저장합니다. 보고서 JSON에 반드시 합치지 않습니다.
- 내부 실행 기록에는 선택값, 정규화 결과, 비용 기준 버전, 계산 결과, 재정 판단, 검색 질의, 검색 근거, 사용 근거 ID를 남깁니다.
- 기존 근거 JSON만으로 생성하는 `src/generation/generate_report.py` 경로도 새 생성 입력 계약과 맞춥니다. 새 계산 정보가 없는 구버전 파일은 명시적인 호환 처리 또는 이해 가능한 오류를 제공합니다.
- 새 입력·출력은 스키마 버전을 식별할 수 있게 합니다. 기존 상세 입력과 이전 결과를 임의 변환·덮어쓰기하지 않습니다.
- 단계별 출력은 실행 식별자를 가진 별도 위치에 보존합니다. 계산 로그에 API 키·비밀정보를 기록하지 않습니다.

## 7. 비용·범위 통제

- 첫 구현은 제한된 비용 기준자료와 기존 코퍼스를 활용합니다. 전국 단위 수집, 새 임베딩 모델, 그래프 DB, 정책 자격 룰엔진은 제외합니다.
- 기존 임베딩·청킹 설정은 변경하지 않습니다. 신규 문서·필수 메타데이터 보완이 생길 때만 적재 필요성을 별도로 확인합니다.
- 사용자가 직접 적재한다는 기존 방침을 유지합니다. 적재 명령이 필요한 단계에서는 대상·영향·실행 명령을 안내하고 자동 재적재하지 않습니다.
- 계산·질의 테스트는 외부 호출 없이 먼저 수행합니다. 유료 생성·RAGAS 실행은 소규모로 시작하고 호출 수·비용을 확인합니다.
- 단계마다 검증 후 다음 단계로 넘어갑니다. 불필요한 새 폴더·모듈을 미리 모두 만들지 않습니다.

## 8. 바로 다음에 할 작업

우선 **0~1단계: 기존 결과 보존과 선택형 입력 계약·시험 입력 작성**부터 진행하는 것이 적절합니다. 특히 다음을 먼저 결정해야 이후 구현이 흔들리지 않습니다.

1. 금액 구간의 선택지와 경계.
2. 없음·모름·예정·미정의 코드와 의미.
3. 보고서와 정책이 공유할 사용자 상황 필드.
4. 기존 정확한 금액 입력·생성 근거 파일의 호환 방침.

그다음 비용 기준자료를 확보하고 계산·판단을 구현합니다. 비용 근거 준비를 생략한 채 생성 프롬프트만 바꾸어 새 구조를 완성했다고 처리하지 않습니다.
